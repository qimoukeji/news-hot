# 重置监控采集、上下文补齐与按串识别

## 目标与适用范围

Codex、Claude、Grok 共用一套处理流程：第三方负责筛选主帖和回复类型，本地接收数据；将随帖引用和父帖关系补齐后，按真实关系组织帖子，一串调用一次识别模型。每个动作仍绑定到具体原帖证据。

本地不再依据回复目标账号是否完整决定是否收录。移除运行中的回复类型重复筛选，不增加兼容开关或第二套采集模式。接口返回的帖子经解析、去重后保存；结构、作者或时间与请求约定不符时记录明确异常，不静默丢弃后宣布采集完整。

本方案覆盖共享采集引擎、两家已支持供应商、模型输入输出、事务保存、后台检查、规则与文档、必要的增量迁移，以及本次 Codex 数据的定点修复。不修改 .env、CI/CD，不推送、不部署、不自动启动真实付费任务。

## 本次案例与验收结果

| 标识 | 帖子 ID | 关系 |
| --- | --- | --- |
| A | 2115273064481218829 | 最初的额度重置预告 |
| B | 2115273253711409208 | 回复 A，补充说明 |
| C | 2115330127886463244 | 引用 B，后续完成声明 |
| D | 2115297093879472332 | 独立的 Poteto 网站帖子 |

B --回复--> A；C --引用--> B。识别输入按发布时间排列为 A、B、C，D 独立。

全新回放时，预期保存四条监控账号帖子，形成两个识别组：ABC 和 D，共调用模型两次。回复或引用关系只决定一起阅读，不代表必然属于同一个额度事件；事件及动作仍按证据判断。

回执 35 的真实响应已经在 C 的 quoted_tweet 中包含 B，并保留 B 的父帖 ID。A 也已在同一响应及数据库中存在。因此这个案例不需要再次购买帖子内容，修复应能从现有材料恢复四条监控账号帖子和完整关系。

实际历史修复时，A、D 已处理，C 为待复核：只将 B 作为新待处理帖子，明确重新处理 C；A 与已有事件、动作作为只读上下文，D 不重跑。预期只进行一次新的 ABC 组识别，保留原事件与动作 ID，不重复创建 A 的预告。

“四条”指四条监控账号业务帖子。A 原有的外部引用等辅助材料仍可作为上下文，它们不计入这四条、不自动成为官方事件来源。

## 完整处理流程

1. 固定本轮窗口，保存采集参数；依平台配置生成第三方查询并完整读取分页。
2. 解析每页帖子及随帖引用，先保存主采结果；ID 去重，不覆盖已接受或人工修改的文案和处理结果。
3. 从返回对象中提取完整引用对象，保留其自身的回复父帖 ID、目标账号、作者、发布时间等必要信息。不能再把引用帖压缩成只有正文的孤立片段。
4. 为待识别帖子补齐必要上下文。依次查询本轮所有响应、同平台已存帖子，再按缺失 ID 请求当前供应商；已有足够材料不再次购买。
5. 跨页合并完成后，再建立回复、引用关系，组织识别组，不能每收到一页就立即识别。
6. 对每组待处理帖子调用一次模型，输入完整必要上下文和相关已有事件、动作。
7. 逐条校验输出证据，按组事务保存接受的事实、每帖处理结果及共享模型回执。
8. 本轮所有采集和识别工作完成后推进成功检查点。独立翻译、确认检查和订阅任务仍独立运行，不合并到采集 tick。

## 第三方筛选与本地接收

主帖、自回复、回复他人的开关继续保留在 site/reset-monitors.ts，并只用于构造供应商查询。本地删除对应的重复类别过滤，inReplyToUsername 为空不影响保存。

实施时首先核验供应商支持的查询语法。当前组合 from:账号 与 (-filter:replies OR to:账号) 的真实结果遗漏过 B，不能直接视为已证明覆盖完整。使用本次案例检查主帖、自回复、回复他人三个集合，以及分页、时间和关键词配置的组合。供应商文档说明语法，但不能替代真实覆盖验证。

不默认改为全量抓取后本地分类，也不以扩大采集范围掩盖问题。若供应商不能可靠表达指定范围，明确列出实测结果和替代查询方式，再决定采集策略。接口覆盖验证不能仅靠本地假服务。

resetOnly 的模型相关性判断与 filtered_out 保留，这是后续业务判断；本次删除的是重复判断来源帖子是否属于允许的回复类型，不取消对额度事实的识别。

## 上下文补齐与保存

查找顺序为：本轮已解析对象、同平台已存帖子、供应商按 ID 查询。信息足够是指能完成当前需要的作者核验、父子关联和内容理解，不因为一个非必需字段为空就再次请求。

补采直接回复父帖、明确引用对象；仍缺必要事实时沿真实父帖链向上补。找到主帖、足够的已存事件上下文后停止。ID 去重，校验父帖不得晚于子帖，检测循环与冲突；不抓整条评论流，不扫描账号历史，不按时间接近拼接。

补采对象可以早于当前采集窗口。外部作者或窗口外材料只作上下文，不因此自动补发历史事件。当前窗口内、属于配置作者的引用或补采帖子可以成为待识别业务帖子；这一过程依据明确引用关系补齐材料，不重新分类自回复。

复用 monitor_source_posts 保存规范化帖子，context_only 布尔字段默认为 false。业务帖子与辅助上下文使用同一 ID 去重，上下文记录不独立进入待识别列表、默认帖子统计、公开来源或自动动作来源。后来被正常主采命中且满足本轮约定的上下文记录，可提升为业务帖子并进入 pending。

reply_to 保存真实父帖引用；quoted_post 保留必要的单层随帖引用快照及关系元数据。分组和关联优先读取已保存的规范化帖子与引用 ID，快照仍用于缺失对象的上下文。相同 ID 的作者、时间或原文出现冲突时，不静默覆盖，记录待处理原因。

不新增永久 thread_id、独立线程业务表或另一套事件模型。按串识别使用现有帖子关系计算；必要的组执行元数据复用 monitor_state，只存 ID、版本、回执引用和执行状态，不复制原文。

所有上下文原文只在后台帖子中保存。供应商原始响应只存在内部付费回执，不进入事件、动作、公开出口或业务审计。

## 按串识别与事实保存

分组依据是可核验的回复和引用关系，不使用相同作者、相似正文或接近时间代替关系。外部引用可以供模型理解，但共享一个外部引用不能把若干官方帖子合并成一串；组始终属于一个监控平台。

每组明确区分 targets 和 context：targets 是本次需要处理的业务帖子；context 是只读的历史帖子、外部材料及已有事件动作。已有 processed 帖子不因新回复出现而重新生成自己的动作。待复核帖子默认不自动重跑，本次 C 的重新处理通过明确的定点修复完成。

模型输入包含每帖 ID、作者、时间、原文、回复及引用关系、只读上下文和相关既有事件动作。每个 targets 必须恰有一份帖子级结果，包含标题摘要、相关性、是否待复核及原因；每个候选动作给出具体 postId 和字面证据。跨帖新事件使用组内一致的 localEventKey，关联已存事件使用真实 eventId。

本地复用现有事实校验、时间解析、范围校验及动作归并。每项事实只能引用对应原帖的证据；上下文用于确定对象和承接范围，不能把别人的话变成官方承诺，也不能把 C 的完成事实记成 A 发布时已经完成。来源冲突或歧义落实到具体帖子及动作，不凭模型猜测强行关联。

先在组内按来源顺序模拟接受的事实，再一次事务保存。支持同组后帖关联本组先帖新建的事件，也支持沿用已有事件。相同事实补来源，不新建重复动作；无来源确认得到官方证据时按现有规则升级同一动作。

同组可以保留有效动作，同时将有歧义的帖子设为 needs_attention；持久化异常则整组回滚。保存前核对 targets、实际使用的上下文和有关事件动作的版本，仅锁本次相关记录。过期模型结果不得覆盖人工修改。

单组序列化输入最多 128 KiB，超出时保留原文并转人工，不发送模型请求。过长或关系异常的串不静默截断后宣布完成，也不为了凑一串一次而发送超限请求，应保存明确原因转人工。本次案例不需要截断或拆组。

## 回执、恢复与检查点

按 ID 补采使用 monitor.context 或对应平台的同类用途，复用现有预算、采集开关、网络保护和付费回执。TwitterAPI.io 可使用 GET /twitter/tweets 按 tweet_ids 查询，SocialData 可使用 GET /twitter/tweets/{id}；供应商适配器统一输出规范化帖子、明确不可用 ID 和回执引用。

按 ID 查询必须按实际返回的 ID 匹配结果，不能按数组顺序对应。TwitterAPI.io 单次最多 50 个 ID；可以合并本轮缺失 ID 请求，但仍逐 ID 核验。接口漏返某个 ID 不等于已经证实删除，应记录为未返回、上下文不可用，不凭空补写删除原因。

同一缺失 ID 去重并持久保存查询结果。成功响应先存回执，再保存业务数据；404、删除或不可访问等明确结果记录原因，相关帖子转复核，不把不存在的父帖伪造成空帖子。网络异常、预算中止和计费未知不当作“没有父帖”，本轮保持未完成。计费未知不自动重复付费。

采集在发起付费请求前持久保存固定窗口和执行标识。某一页失败后，本轮立即结束，不在本轮自动重试；下一次独立定时任务继续同一个窗口、查询与逻辑回执 key，已收到并保存的页面直接复用。只有已明确未受理的 HTTP 拒绝，才允许下一次任务在同一 key 下追加一次尝试；仍须重新检查预算和安全阀。计费结果为 unknown、曾有 unknown 尝试，或已经收到收费响应但 schema 无效的请求，都不得自动重发，也不能通过换 key 绕过。固定窗口全部采集与识别持久完成后才推进截止并清除窗口状态。

组识别请求绑定目标 ID 与版本、上下文和已有事实版本、模型、提示词及配置。请求前保存稳定执行标识；数据库写入失败后复用 received 响应，不生成新的随机标识重复购买。多帖可以引用同一个模型回执，不能把一次模型调用计成多次。

结构错误、业务歧义按现有待复核规则保存，不自动重买同一输入版本。恢复时跳过已完成组，不重识别已有结果。只有本轮所有组都已得到持久化结果，成功截止才推进；needs_attention 属于已完成自动处理但需人工判断，pending/failed 或未完成上下文请求阻止推进。

任务日志区分搜索返回数、从引用补入数、付费补采数、业务帖子数、辅助上下文数、识别组数、模型调用数、待复核数、新增或更新的事件动作数，避免把“任务无异常退出”表述为“上游检索一定没有遗漏”。

## 正式运行的质量与费用控制

正式任务的技术完成与业务判断分别展示。返回已处理、待人工处理、技术失败、结构失败组数和是否采集完整；待复核不伪装成全部识别通过。结构失败记录字段路径与错误类型，不把原文或完整模型响应写进任务日志。成功游标仅在采集、上下文及所有组结果持久完成后推进。

站点可为某个平台配置每轮新增搜索页数上限；Grok 设置为 5 页，跨配置账号合计，已收到且复用的页面不重复消耗页数或费用。达到上限且仍有账号或下一页时保存原固定窗口、续采账号及分页游标，返回采集未完成；不推进成功截止，不提前识别不完整线程。下一轮从未完成位置继续。最后一页没有下一页且全部账号完成时，正常进行上下文及识别。

配置位于 `site/reset-monitors.ts` 的 `collection.maxPagesPerRun`，必须为正整数，省略表示不限制新增搜索页数。`paidPages` 与 `reusedPages` 区分本次新请求和回执复用，`windowPages` 表示固定窗口已持久保存的累计页数。

完成句判断按明确事实分句处理，允许 And 等自然连接词，仍拒绝否定、条件、未来承诺及个人感受。午夜与中午按来源时区和日期解析，PST 固定 UTC−08:00，PT 使用 America/Los_Angeles；截止时间不得冒充实际完成时间。

线程模型使用统一的完整输出结构，帖子级和动作级字段分开。仅对真实响应中已出现且确定无语义的帖子级 `scope:null` 冗余字段作定点清理；非空范围、未知字段、遗漏目标和错误事实仍严格拒绝。已有有效标题摘要应尽量保留，并显示具体结构错误。

模型请求记录输入材料的组成、字符数和实际 token 用量，以区分提示词、目录、上下文和已有事件的开销；不为节省输入而截断必要关系。没有帖子时不调用模型。零返回只表示查询无结果，诊断应保留账号、窗口、筛选条件和分页覆盖情况。

已有动作只给模型一份可读文案，优先英语、其次中文及其他可用语言；原记录仍完整保留七语言。模型输入中的动作 ID、顺序、来源、业务状态与事件关系保持不变。字符组成属于诊断量，实际 token 和费用仍以付费回执及供应商账单为准。

真实付费回执可用于明确授权的定点结果恢复：先备份、只读预览、核对目标与现有事实版本，再将保存的响应重新通过当前结构、事实和关联校验。旧回执和既有事件动作 ID 保留，历史修复不补发通知，不重新采集或购买相同模型输出。该恢复不成为常规 worker 自动购买或读取原文的新入口。

## 验收与执行顺序

先修改规则和设计文档，再改代码及测试。开发分支保持 dev/codex。新增数据库字段、迁移和历史数据修复须获得明确授权；方案确认不代替生产部署或新的真实付费运行授权。

关键验收：

1. 用回执 35、36 脱敏后的真实结构作本地回放，B 即使目标账号为空也能保存，四条业务帖子形成 ABC、D 两组。
2. A、B、C 跨页、乱序或重复返回仍只保存一次，按明确关系组织；D 不被误拼入。
3. B 可从引用恢复时不调用补采接口；本地完全没有父帖时才按 ID 补采，多帖共用父帖只买一次。
4. 删除、不可用、缺少 ID、网络异常、预算不足和计费未知分别处理，不无限补采、不静默丢失。
5. 外部作者、窗口外历史和仅上下文记录不自动生成官方动作；一个串中的不同事实可以属于不同事件。
6. 全新 ABC 只调用一次模型；三帖的每项事实与各自来源对应，支持组内事件引用；输入输出完整且不串平台。
7. 人工修改、事务失败及进程中断不会产生半组写入、重复动作或重复购买；received 回执能够恢复写入。
8. 本次历史修复只新增 B 并重审 C，沿用 A 的事件与动作，D 不重识别；不回退检查点，不发送历史通知。
9. 运行 typecheck、独立测试库中的测试、Web 构建与测试，以及站点启动后的 smoke；所有自动测试只使用本地假服务。
