# Codex 重置监控

跟踪 `@thsottiaux` 的 Codex 额度重置与重置卡消息，提供公告、预计北京时间窗口、到账证据、关联原帖和历史日历。后台支持修正、撤回、关联调整和人工到账核验。预计窗口结束后仍保留“未确认”标记。

## 配置

在 `.env` 或采集凭据文件中配置，修改后重启 API 和 worker：

```dotenv
CODEX_RESET_PROVIDER=twitterapi_io
CODEX_RESET_SCAN_MINUTES=15
TWITTERAPI_IO_API_KEY=<your-key>
# TWITTERAPI_IO_BASE_URL=https://api.twitterapi.io
# 也可选择 socialdata，使用以下配置：
# SOCIALDATA_API_KEY=<your-key>
# SOCIALDATA_BASE_URL=https://api.socialdata.tools
# 可选 MONITOR_MODEL=deepseek-flash，需配置对应模型凭据。
```

开发预览保持 `COLLECT_ENABLED=false`、`MODEL_CALLS_ENABLED=false` 和推送安全阀关闭。页面查询只读数据库。实际采集需要启用采集安全阀，识别另需模型安全阀；worker 默认每 15 分钟扫描一次，`CODEX_RESET_SCAN_MINUTES` 支持 1、2、3、4、5、6、10、12、15、20、30、60 分钟，修改后重启 API 和 worker。页面和 Agent 查询说明使用同一后端配置。每天北京时间 04:40 回查最近 24 小时。付费请求使用框架回执和后台请求预算；TwitterAPI.io 初次使用沿用 SocialData 的预算上限，后续可单独修改。

两种源都通过采集凭据组读取各自的 `API_KEY` 和可选 `BASE_URL`，地址留空使用上述官方默认值。`BASE_URL` 填 API 根地址，不包含 `/twitter/search` 等端点路径。配置 `EGRESS_PROXY_URL` 时，两种源均使用现有的安全代理解析和连接路径；未配置代理时直接连接。

模块在 `site/modules/` 的三份清单中安装。仓库迁移命令创建四张监控表及两个索引，历史迁移保持原样。首次启用没有历史运营数据，日历从实际保存的帖子开始。

正常采集范围为上次整轮成功的截止时间到本轮开始时间，使用 `since_time` 与 `until_time`。没有成功检查点的采集源不能运行普通扫描，任务在付费请求前中止，必须先指定有限时间范围初始化；新安装、切换提供商或旧截止时间没有整轮成功证据时都一样。

从仓库根目录执行以下命令。将两个时间替换成使用者确认的采集范围，必须是带时区的 ISO 时间且 `since < until <= 当前时间`；命令读取现有 `.env`，不修改配置：

```bash
npm run initialize -w @aihot/codex-reset -- --since 2026-10-08T00:00:00Z --until 2026-10-09T00:00:00Z
```

初始化前需要明确启用 `COLLECT_ENABLED=true` 和 `MODEL_CALLS_ENABLED=true`，并配置采集源、模型凭据及请求预算；该命令会实际调用采集和模型。Docker 部署使用相同 npm 命令：`docker compose run --rm worker npm run initialize -w @aihot/codex-reset -- --since <已确认的ISO时间> --until <已确认的ISO时间>`，时间参数替换成实际值，环境与凭据沿用现有部署。参数、开关、已有成功检查点或并发任务不符合要求时，以失败退出且不会建立新检查点。

每页成功立即保存帖子，所有页面、必要上下文与待识别帖子全部成功才建立或推进截止时间。初始化不会提高预算、自动缩短范围或直接写入水位；范围超过预算时同样失败，已保存帖子保留，使用者应根据运营范围和现有预算明确安排初始化。初始化成功后，普通 worker 自动从其 `until` 继续扫描；业务上的待人工复核不阻止本轮成功，每日 24 小时查漏不建立或推进正常扫描截止时间。

任一步请求失败或结果未知都标记失败并中止本轮，后续步骤不执行；下一轮正常扫描从上次成功时间重新查询，已保存帖子去重，已处理帖子不重复识别。不使用回执恢复、30 分钟自动放行、重试次数、手动再次补采或跨轮分页续跑。每轮使用独立付费回执；结果未知时回执执行状态为失败，请求尝试中的计费未知仍保留，不代表没有扣费。预算不足和 HTTP 402 同样中止，需要预算恢复、充值或切换有余额的源后，由下一轮正常采集补齐。

上下文优先复用本地帖子和已有内容，未完成的回复保留 `raw.contextPending`。上下文或识别失败记录在帖子详情和运行记录中，不作为业务复核。识别按发布时间处理，等待必要上下文完整；人工完成的帖子不再由 worker 识别。普通扫描和每日查漏共用数据库执行互斥，已有任务运行时跳过重叠任务。标准 worker 的监控队列不自动重试；更新时已有队列及排队任务也设为零重试，旧的待重试任务结束为失败，运行历史保留。

TwitterAPI.io 使用框架的出站连接路径；配置 `EGRESS_PROXY_URL` 时通过该代理解析和连接，仍验证目标为公网地址。
免费账户要求请求至少间隔 5 秒时，可设置 `TWITTERAPI_IO_REQUEST_INTERVAL_MS=5500`；默认值为 `0`，请求预算仍单独生效。

`collectPosts` 保存主帖及响应内引用内容，回复上下文另由 `collectPendingContext` 获取。旧帖已保存上下文继续使用。框架代理 DNS 解析超时为 30 秒，TwitterAPI.io 整体请求超时为 60 秒。


## 入口

识别按实际事件抽取，同帖重复表述通过 `duplicateOf` 指向前一个命题（从 0 开始编号）；多个缺少区分依据的同类确认转复核，不自动新建多件事件。明确多轮且各轮归属可确定时保存各轮；多轮动作只提供一个目标或不能确定各轮归属时，保留次数并说明原因，整条动作转人工复核。进展与确认补全事件的形式、产品和适用对象，未知字段不覆盖已有信息。回复和引用原帖已关联的历史事件优先提供给模型，不受最近确认 48 小时或预告 72 小时窗口限制；这些事件必须未撤回且不晚于当前帖子，线程关联的多轮事件全部保留，另外最多提供八个近期候选。关联优先使用明确事件 ID；“第二次已完成”或重复强调不会丢弃有效目标。同类候选有多个且不能区分时转复核。时间窗口遵守原话截止时间，未给时间时的推算单独标注，时间经过不代表确认完成。

命题记录 `role`（明确动作、直接回答、解释、政策或不确定），解释与条件政策不生成事件，未明确承诺的惊喜、Maybe、玩笑和惯例按相关或无关处理，不仅因暗示转复核。进度与确认只补全未知适用对象，已有范围通过明确的补充说明更正，Business 子集下发不会改掉全员对象。`timeSourceId` 记录相对时间原文的帖子：短回复继承直接父帖的“明天”等日期，来源时间缺失或晚于回复则转复核。明确的“18:00”保留单个钟点；只有原话给区间才展示区间。明确完成的复数表述按默认一轮记录，形式不明单独标注，不能因此编造具体次数或到账证据。

同帖“another one”只能继承前面可在原文核验的同类重置动作；未满足的 if/unless 条件和 either/or 政策不能当作预告。“instead granted”明确解释同次补偿时，合并数量与对象条件并保存 `duplicateOf`，不能增加事件数；没有明确重复证据的第二个确认仍转复核。`relatesTo` 必须使用提供给模型的事件 ID，不能用上下文原帖 ID 或自行编造 ID 关联事件。

解释自动应用原因时，主帖明确说已应用、直接父帖也描述已应用，并且线程中的 Tibo 原帖已关联到同一待完成事件，才允许确认该事件；这种解释不能新增轮次。错过计划时间的原因说明不当作另一次完成。

模型请求参数优先使用所选模型的配置，未配置才用流程默认值。默认模型支持 `LLM_TEMPERATURE`、`LLM_MAX_TOKENS`（思考与答案的总输出上限）、`LLM_TIMEOUT_MS`；`LLM_EXTRA_JSON` 的同名请求字段优先级更高，显式思考配置不会被监控覆盖。未配置温度时监控用 0.1；未配置总输出上限时用 6000 加配置的思考额度；未配置超时时用 120 秒。只有未明确配置思考模式且没有思考预算的 `deepseek-flash` 才默认关闭思考。模型调用仍经过回执及预算。离线规则评估只使用已保存帖子和上下文，不调用付费接口；实帖输入、标注与报告保存在 `.data/local-preview/`，不自动写回生产识别结果。

| 入口 | 用途 |

| `/codex-reset` | 当前监控与日历 |
| `/codex-reset/history/YYYY-MM-DD` | 北京时间某天记录 |

## 新增采集源

在 `backend/providers/` 实现 `Collector` 的 `searchTweets`、`getTweet`，把上游结果转换为统一 `Tweet`，在 `collectors.ts` 注册名称。付费调用必须使用回执、预算和采集安全阀。各源拥有独立成功检查点和覆盖时间，帖子以 X ID 去重。

TwitterAPI.io 对接依据：[搜索与游标](https://docs.twitterapi.io/api-reference/endpoint/tweet_advanced_search)、[按 ID 读取帖子](https://docs.twitterapi.io/api-reference/endpoint/get_tweet_by_ids)。原始响应先保存到回执，再校验和转换；无效结果中止本轮且不推进成功检查点，下一轮正常扫描使用独立回执。请求成本暂不填金额，后台按请求次数熔断。

## 后台人工复核

事件和帖子列表每页 10 条，分页统一放在列表下方，显示总数与页数；空列表也显示总数与页数。帖子支持相关、无关、需复核、待识别和全部筛选；待识别不计入无关。
事件支持“需回执核对”筛选，只显示未撤回、尚未确认且没有确认关联的事件，与“回执核对确认”按钮使用相同条件；切换筛选回到第一页，总数和页数按筛选结果计算。

所有帖子通过“人工复核”进入 `/admin/monitor/posts/:id/review`：先查看原帖、上下文、模型依据和人工记录，再选择无关、相关但无事件动作或包含事件动作，调整译文、故障判断、动作类型、范围、时间和关联事件。关联目标独立搜索及分页，不限于列表当前页。 默认保留目标事件的人工字段；明确勾选覆盖时，预览并提交本条动作的类型、范围及时间，可清空错误字段。

预览列出关联增删、事件字段、确认状态和撤回影响，填写理由后一次事务提交。预览不写数据，不调用模型或采集。提交核验帖子与事件版本，变化时要求重新预览，失败不会部分保存。原模型结果与人工审计保留，旧“已核实”标记不能代替实际复核。

同一摘录包含不同动作时，各动作分别保留其事件关联，重开复核不会串用事实或复制动作；历史关联存在歧义时要求人工明确目标。草稿最多 100 条动作，总轮数最多 100。已撤回事件的本帖原有关联可保留并编辑译文，也可移除，事件继续保持撤回；其他帖子不能新增关联到已撤回事件。

更正帖子时同步修正关联事件：失去唯一事件依据撤回；失去唯一官方确认、但仍有预告依据时退回已宣布；其他官方确认或账户核对仍有效时保留确认。官方确认依据必须来自原帖，账户核对使用独立入口。事件已经确认、有确认关联或已撤回时，不再允许“回执核对确认”。人工更正不发送事件通知。

公开事实统计只计有确认依据的事件；日期统计需要已知确认时间或实际生效日，不把推测完成、预计时间或创建时间当作实际发生。撤回和错误关联不会继续出现在公开确认动态中。
